A Executive summary

Market OS is a mature, carefully built application. The parts that usually go wrong in a multi-tenant POS — concurrent stock, price integrity, cross-tenant leakage in the CRUD routes, subscription bypass — were right from the start, and demonstrably so. 44 API routes were inventoried and every one enforces authentication; every [id] route resolves the record through findFirst({ where: { id, organizationId } }) before touching it.

Six real defects surfaced under execution. Two were fixed during the audit itself; the remaining four — one of them the release blocker — were fixed in a follow-up remediation pass. Every fix reused a pattern already present in the codebase rather than introducing a new mechanism.

The blocker, and why it is closed. The cashier PIN login screen sent only a name and a PIN, and the server resolved that name across every organization in the database. Two customers employing someone with the same name locked each other out, and because any visitor could list any organization's staff without logging in, locking out a competitor's cashiers was a two-minute exercise. Login is now scoped to exactly one organization, established once per device through the terminal cookie the product already set but never read. Two tenants can now share a staff name and work independently; neither one's PIN opens the other's till.

What remains is a short P3 list and two testing gaps, both recorded plainly in sections T and U rather than papered over.

H Inventory

Stock is a Float, which is correct for a grocery selling by weight, and every movement goes through applyStockDeltas — a guarded, id-ordered decrement whose precondition lives in the SQL WHERE clause. Two invariants were checked against live data rather than reasoned about:

  • Stock never goes negative. Draining to exactly zero succeeded; the next unit was refused with 400; the final reading was 0.
  • Units sold reconcile with units removed. Summing every SaleItem.sasia for the tenant matched the fall in Product.sasia exactly, to floating-point tolerance.

Archiving is a soft delete used when a product has sale history. The product list filtered on it, but the sales route did not — so an archived product remained sellable by id. That is now enforced server-side before the transaction opens.

I Supplies & suppliers

Supplies increment stock inside a transaction, in ascending product id, matching the sale path so the two cannot deadlock against each other. Quantities and purchase prices were validated. The defect was in what was not validated: the ids themselves.

Before the fix, a supply could name any product or supplier in the database. The line item was created — the foreign key only requires the row to exist somewhere — the response echoed the other tenant's product and supplier names back through its include, and the stock increment silently matched zero rows, recording goods received that never entered anyone's inventory. Referenced ids are now resolved in one organization-scoped query and the basket is refused with 404 if any is not the tenant's own.

Deleting a supply reverses its stock correctly and is organization-scoped. Supplier create, edit and delete are scoped throughout.

L Dashboard & analytics

The dashboard computes from SQL aggregates — _sum, _count, groupBy — directly against the same tenant-scoped rows the POS writes. There are no denormalised counters, which structurally rules out the most common class of reporting bug: a dashboard total drifting away from the transactions behind it.

What it got wrong was when a day starts. Boundaries were built with new Date(y, m, d), which uses the server's local timezone — Albania in development, UTC on Vercel: 

Sale at 00:30 Albanian time on 14 August

  before, dev  (Europe/Tirane)   "today" starts  2026-08-13T22:00:00Z  → counted on 14 Aug ✓
  before, prod (UTC)             "today" starts  2026-08-13T00:00:00Z  → counted on 13 Aug ✗
  after,  both                   "today" starts  2026-08-13T22:00:00Z  → counted on 14 Aug ✓

All boundaries now resolve explicitly against Europe/Tirane through a shared module, including the daily and monthly chart buckets, so a figure the owner reconciles against the till no longer depends on which machine produced it.

M Notifications & audit

This was checked for one specific failure, and the codebase gets it right. logAuditAction and createNotification both run after the sale transaction commits, and both swallow their own errors internally. That matters more than it looks: if either could throw, the sale would already be committed while the request returned 500, the idempotency claim would be released, and the cashier's retry would create a second sale for the same basket. It cannot, so it does not.

The low-stock scan is queued as a background job rather than awaited, so a cashier never waits on it. Audit entries record the classified error code rather than the driver message, deliberately — audit entries are rendered in the UI, and a raw Prisma error carries table and constraint names. Notifications and audit rows are organization-scoped throughout.

N Backup, export & restore

Code-verified — no restore was executed. Running one requires an Administrator's Supabase session and deletes the tenant's data before rebuilding it, so it was reviewed rather than run.

Backup and export are correctly scoped: every collection is filtered by organizationId, directly or through its parent relation. Restore is guarded well — a strict shape validator, a 50 000-row ceiling checked before any deletion, a cross-organization confirmation prompt, one restore at a time per organization, and a single transaction so a partial failure rolls everything back.

Three behaviours the owner should know about, none of them blocking:

  • A restore erases the organization's entire audit log before rebuilding. An Administrator can therefore clear their own accountability trail through a normal product feature.
  • A restore renames the organization to the name stored in the backup file — surprising when restoring a cross-organization backup that was explicitly confirmed.
  • Restored sales lose staffId and staffName, and restored products come back unarchived. History survives; attribution does not.

Code-verified — reviewed as source, not driven in a browser. No live click-through, mobile-viewport or accessibility audit was performed, and that gap is recorded honestly in section T rather than papered over.

What the source does show, on the screen that matters most:

Required rollout step

Existing devices carry no pos_terminal_org cookie, so PIN staff will see "Kjo pajisje nuk është e lidhur me një market" until a Manager or Administrator opens /personal and clicks Konfiguro terminalin once per till. R Bugs found — all fixed

BUG-01 was P1 — High Fixed & verified

Staff PIN login resolved an identity across every tenant

Workflow
Cashier PIN login — the entry point to the POS.
Original evidence

Executed. Two disposable organizations, each with a staff member of the same name. POST /api/staff-auth/login returned 409: "Ka më shumë se një punonjës me këtë emër." Neither cashier could log in.

Executed. A uniquely named staff member with a correct PIN, sent with no organization context whatsoever, returned 200 and a valid session.

Root cause
prisma.staff.findMany({ where: { emri, isActive: true } }) carried no organizationId filter — because there was no organization context anywhere in the flow to filter by. The login page posts only { emri, pin }.
Impact

Accidental. Two customers employing someone with the same name locked each other out, and neither business could fix it, because the conflict was with a company they could not see.

Deliberate. Self-service registration creates a live trial organization with no approval. Combined with the open staff directory (BUG-02), an attacker could list a real customer's cashier names, create staff with those names in their own trial org, and lock that customer out of their till — with a single paying customer on the platform.

Fix

Reused the mechanism the product already had and never read. POST /api/staff/terminal sets a pos_terminal_org cookie, is invoked from /personal under "Konfiguro terminalin", and then opens the login page. A new getOrgContext() helper reads and validates it; the login route now requires it, checks the organization exists and is active, and scopes the lookup.

On forgery: the cookie is not a credential and is not treated as one. It selects which tenant to authenticate against, exactly as a subdomain would — forging it still requires a real name and PIN inside the named organization, and the session takes its organizationId from the staff row in the database. Rate limiting, lockout, permissions and session issuance are untouched; scoping makes the lockout counter per-tenant, which is strictly better.

src/lib/staff-auth.ts, src/app/api/staff-auth/login/route.ts
Regression
All seven required scenarios executed and passing: both tenants authenticate independently with the shared name; neither PIN opens the other's till; missing context fails safely; four forms of invalid context fail safely; a forged context grants no access; every session is bound to its own tenant. 18 checks in total.

BUG-05 was P2 — Medium Fixed & verified

Day boundaries followed the server's timezone, so production and Albania disagreed

Workflow
Dashboard totals, sales history period filters, exports, audit-log date filters, month and year comparisons.
Original evidence
Executed. The same boundary arithmetic under two timezones — see the measurement in section L. A sale at 00:30 Albanian time was attributed to the previous day in production and to the correct day in development.
Root cause
new Date(y, m, d) resolves against the process timezone. Vercel runs UTC; no TZ was configured.
Fix

A new src/lib/business-time.ts resolves boundaries explicitly against BUSINESS_TIMEZONE (default Europe/Tirane) using Intl.DateTimeFormat. Two properties the callers depend on: day boundaries are calendar arithmetic, never +86400000, because DST days are 23 and 25 hours long; and a wall-clock time resolves its zone offset twice, at the guess and at the candidate it produces, so results land on the correct side of a transition.

process.env.TZ was deliberately not set — it would fix the symptom while leaving the code dependent on ambient state. No stored timestamp is written or altered; only the boundaries used to group and filter them.

U Remaining issues & risks

P0: none. P1: none. P2: none. The list below is P3 and testing gaps only.

P3 issues

  • Restore erases the organization's audit log and renames the organization to the backup's name; restored sales lose staffId and staffName. Acceptable for a single-owner shop, worth revisiting if larger customers arrive.
  • PIN entropy. A 4–6 digit PIN is the only secret protecting a till. The 5-attempt lockout is the mitigation and it holds — but it also means a brute-force attempt locks the real cashier out as a side effect.
  • Rate limiting trusts x-forwarded-for. Correct on Vercel, which sets the header itself; it would be spoofable in a self-hosted deployment without a trusted proxy in front.

Testing gaps

  • The UI is unverified in a browser. Everything in section P is source review. A click-through on a real tablet before launch is worth the hour.
  • Manager and Administrator paths are code-verified only. Their isolation follows the same pattern as the routes tested live, but the pattern was confirmed by reading, not by execution.
